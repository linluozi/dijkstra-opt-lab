# 原始包审阅记录

> **这是对修复前的版本做审阅时留下的记录，不是当前仓库的测量结果。**
> 文件名里的历史数字（例如 96.7 倍）来自缺少负边校验、且堆里只存两元组的旧实现。
> 它少了一层安全检查，理论上应该略快，但**无法与现在的数字直接对比** ——
> 这份仓库自身的跨运行漂移就超过了这个差距（同一份代码两次跑，16k 那行可以差 20%）。
> 当前实现的权威数据见 [主 README](../README.md) 和 `results.json`。

审阅对象：一份 5 文件、499 行、纯标准库的 `optimized_dijkstra` 包
（`README.md` / `benchmark.py` / `dijkstra_naive.py` / `dijkstra_optimized.py` / `requirements.txt`）。

## 一句话结论

优化方向对，算法结果正确，加速真实存在 —— 但它自带的 benchmark 把测试图形全选在了
最不利于堆版本的场景上，峰值只有 3.3x，而它的 README 宣称"稀疏图加速数十到数百倍"。
不是优化没效，是**结论走在了证据前面**。

## 一、原包 benchmark 的输出（已复现）

| N | E | naive | heap | speedup |
|---:|---:|---:|---:|---:|
| 50 | 473 | 0.10 ms | 0.08 ms | 1.2x |
| 100 | 1 483 | 0.28 ms | 0.22 ms | 1.3x |
| 200 | 3 969 | 0.98 ms | 0.55 ms | 1.8x |
| 400 | 7 941 | 3.13 ms | 1.22 ms | 2.6x |
| 800 | 19 009 | 10.89 ms | 3.30 ms | **3.3x** |
| 1 500 | 33 752 | (skipped) | 6.16 ms | — |

峰值 3.3x，与 README 的"数十到数百倍"差一个数量级。

原因在 `configs`：从 `(50, 0.2)` 到 `(1500, 0.015)`，边数始终约为节点数的 24 倍 ——
**全是稠密图**，恰好是堆版本最不占优的场景。

## 二、换到稀疏图后

| V | E | naive | heap | speedup |
|---:|---:|---:|---:|---:|
| 1 000 | 3 993 | 15.1 ms | 1.51 ms | 9.6x |
| 2 000 | 7 990 | 65.6 ms | 4.71 ms | 13.7x |
| 4 000 | 15 986 | 289.9 ms | 10.33 ms | 23.6x |
| 8 000 | 31 988 | 1 003.3 ms | 21.87 ms | 42.6x |
| 16 000 | 63 994 | 6 652.5 ms | 64.96 ms | **96.7x** |

V 每翻一倍比值涨约 1.5-1.7 倍，正是 `O(V²) / O(E log V)` 该有的形状。
"数百倍"要 V ≈ 5 万才可能，当时没有任何证据。

## 三、README 里的一处理论错误

原文复杂度表把 naive 标为 `O(V² + E)`、heap 标为 `O((V+E) log V)`，然后写
"**稠密图也显著提升**"。

代进去：`E = Θ(V²)` 时 naive 是 `O(V²)`，heap 是 `O(V² log V)` —— 后者渐近**更大**。
稠密图上那 1.4-2.7 倍全部来自常数因子，不是复杂度优势，所以它会随规模趋平而不是拉大。

这条结论后来被固定成仓库里的密度扫描实验（`benchmark.py` 的 `density_sweep`）。

## 四、四个静默缺陷

1. **`dijkstra_optimized_all` 缺负边校验。** 同文件的 `dijkstra_optimized` 有。
   负边图上 `_all` 静默返回 `4: 2.0`（真实值 `-2`），另一个函数抛 `ValueError`。
2. **堆里存 `(距离, 节点)`。** 距离相等时比较节点本身，混合类型节点直接 `TypeError`。
   线性扫描版在同样输入上正常 —— 这是优化引入的退化。
3. **`end=None` 返回 `([], 0.0)`。** `0.0` 是编造的距离，与 docstring 的
   `inf if unreachable` 自相矛盾。
4. **两个 `_all` 的返回键集不同。** naive 含 `inf` 全节点，heap 只含可达节点。
   README 把"只处理可达节点"写成优化点，却没标 breaking change。

外加两处小的：

- `dijkstra_optimized.py:40-42` 是死代码 `if start not in graph and (...): pass`。
- `optimized({}, 'x', 'x')` 返回 `(['x'], 0.0)`，naive 返回 `([], inf)`。

## 五、原 benchmark 的方法学问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | configs 的 `E/V` 恒为 ≈24，全稠密图 | **最主要**，选在最不利场景 |
| 2 | 单次计时，无 best-of-N | 噪声直接进表 |
| 3 | 同轮顺序跑，不交错 | 无法排除漂移 |
| 4 | `V = 1500` 那行 naive 被跳过 | 复杂度对照在最大点恰好缺证据 |
| 5 | `assert abs(d1.get(0,0) - d2.get(0,0)) < 1e-9` | **假断言**：源点到自己恒为 0，永远成立 |
| 6 | 只预热 optimized | 实测偏差约 10%（这一步是低估比值），非主要项 |

第 5 条尤其值得注意 —— 它看起来在验证正确性，实际零信息量。

## 六、对的部分

- 算法结果正确：80 节点随机图上 4 个源点全节点距离一致，路径重建也对。
- 惰性删除（重复入堆 + `visited` 跳过过期条目）是 Python 下的标准做法。
- 早退逻辑（目标出堆即停）实现正确。
- 可读性确实比 naive 版好。
